# 智研引擎 Demo 开发计划书

版本：V1.0  
编制日期：2026 年 10 月 19 日  
文档状态：开发前交接基线  
配套文件：AGENTS.md、02_开发提示词.md

本计划用于把现有申报书、V0.3 需求说明书及 HTML 原型转化为可执行的开发任务。交付目标是一个本地可运行、数据可保存、流程可验证的智研引擎 Demo。第一优先级是稳定的需求身份与版本、工程师确认、需求变更后的下游复核和评审证据，而后完成页面、规则与演示体验。

本计划中的 P0/P1/P2、数据模型、测试门槛、接口和工期均为本次提出的实施方案；原始业务要求以资料 S1、S2 为依据。尚未确认的事项按下列默认假设推进，不将假设描述为用户已确认的条件。

## 一 项目目标与默认假设

### 1.1 交付目标

以法士特—陕汽重型变速器定制变型项目为示例，贯通需求解析、变型设计、试验验证三个智能体，以及一致性检测和协同风险提示两个贯穿引擎。用户能看到每份产物的来源、依赖版本、确认状态和后续影响，并在一次 2600 → 2800 N·m 需求变更后完成复核与材料汇编。[S1 实际 PDF 第 1、2、5 页；S2 第 1、8 节]

首版同时满足四项结果：一套可重复演示的业务场景；一套真实运行的规则和状态流转；一套经过 TDD 与端到端验证的代码；一套可供他人安装、复现和继续开发的交付材料。

### 1.2 默认假设

| 编号 | 当前采用的假设 | 对范围的影响 |
| --- | --- | --- |
| A01 | 本地单用户业务演示，演示对象和截止日未确认 | 默认绑定本机地址，不安排公网部署和生产 SLA |
| A02 | 使用合成或已脱敏数据 | 不依赖获取企业真实数据才能推进；示例参数不作为工程结论 |
| A03 | 未提供可运行的完整后端仓库 | 保留原型参考文件，建立分层实现；若后来提供仓库，先兼容既有架构 |
| A04 | 核心流程不需要真实大模型密钥 | 默认 rule/mock 模式，明确标注；真实模型接入单列后续任务 |
| A05 | 人工确认使用本地演示身份 | 记录身份与意见，不将角色切换宣传为认证授权 |
| A06 | 依赖和浏览器可事先安装 | 安装完成后的核心运行与测试可离线，不承诺空白环境离线安装 |

演示对象、截止时间、已有后端、企业样例与真实模型条件均为待补信息。在没有新指令前，开发者按 A01–A06 完成 P0；不得因这些非阻塞问题只停留在提问或计划阶段。

## 二 现有资料与开发起点

### 2.1 资料分工

S1 申报书提供项目价值、总体架构、技术路线和目标指标。S2 V0.3 说明书提供模块、输入输出、示例和演示步骤。S3 原型提供页面结构、交互雏形和部分规则实现。功能以 S2 为主要依据，业务背景回查 S1，S3 不具有证明算法或后端已经实现的效力。

S2 标记 ▲ 的功能是待确认的扩展建议。其余要求也需要按本计划区分首版真实实现、受控模拟和后续工程化；不能把某一功能的页面存在等同于其真实算法已经完成。[S2 第 1.4、7 节]

### 2.2 原型可复用部分与已知问题

可复用内容包括中文工业工作台风格、九个页面区块、项目切换、需求编辑与确认、设计与试验列表、风险事件管理、CSV 导出及 JSON 备份思路。[S3]

开发前将以下已发现问题写成回归测试，并在新实现中解决：

- 原型仅提取六类固定参数，S2 的技术协议示例不能直接解析出有效需求。
- 重新解析会沿用部分旧确认状态，关联设计审批和试验值未正确失效。
- 部分编号由数组顺序生成，删除、新增或重解析可能产生重复 ID。
- 比较符、千位分隔符及温度范围存在错误判定风险。
- “未确认”可能遮蔽已经发现的失败结果；审核状态与检测状态未分离。
- 型谱匹配、独立 FMEA、样件与报告比对、完整评审材料包尚缺。
- 原型预留 /api/health、/api/state、/api/parse，但附件中没有对应后端；页面说明不等于服务已经存在。

这些是源码和关键函数检查形成的开发输入，不是完整浏览器、性能或后端联调报告。M0 应在实际开发环境重新建立可复现基线。

## 三 范围与能力边界

### 3.1 P0 必须完成

P0 建立真实本地前后端和持久化，完成一个项目从协议到评审材料的闭环。真实实现包括输入校验、文本文件抽取、结构化规则、受控候选库匹配、版本依赖、确认与审计、冲突规则、沟通指标计算、追溯矩阵和材料导出。对模型语义、复杂生成及视觉推断，可以使用确定性模拟适配器，且必须对输入和模式负责。

| 输出编号 | 首版交付内容 | P0 能力方式与边界 |
| --- | --- | --- |
| O1 | 结构化需求表、来源、状态与版本 | 真实文本抽取及规则；支持 A–I 九类字段组织，冻结样例字段并允许人工补全 |
| O2 | 推荐基型及逐项依据 | 从至少三条合成候选数据计算；不足三条时如实返回，区分满足项和待变型项 |
| O3 | 变型点清单 | 由选定基型与需求差异真实计算，记录影响零件和上游版本 |
| O4 | 可复用件清单 | 受控零件清单中标记沿用、修改、新设计；供应商责任细化属于 P1 |
| O5 | 待澄清问题单 | ▲ 完整派发与答复流程列 P1；P0 必须显示缺失、模糊和冲突问题并阻止误通过 |
| O5′ | 供应商需求传递清单 | ▲ P1，不自动发送至任何外部组织 |
| O6 | 相似历史项目推荐 | 从合成历史库检索并解释相似点；不假称真实企业检索 |
| O7 | 设计评审清单 | 生成草案，含检查要点、标准、责任演示身份、依赖和独立确认 |

| O13 | 门径评审材料包 | 真实冻结快照并导出，包含版本、问题、审核和模式，不以 JSON 备份替代 |

上述 O 编号沿用 S2；P0 实施深度和能力方式为本次建议。门径材料是阶段评审所需的证据集合，不代表已取得真实工程或企业验收。

### 3.2 P1 和 P2

P1 为增强功能：▲ 三方澄清与派发流程、供应商责任细化、按供应商与批次深化看板、旧原型数据迁移、更多领域样例、可编辑的办公格式材料。按优先级追加，不影响 P0 闭环验收。

P2 为企业工程化：私有化大模型微调与真实 RAG、OCR、真实图纸识别与样件视觉推断、时序风险预测模型、PLM/企业微信/钉钉生产连接、真实身份认证与对象级授权、多用户并发、生产监控和部署。应基于实际数据、接口与授权重新估算。

### 3.3 不属于本次首版的任务

不自动生成可制造的完整 CAD 设计，不执行真实强度仿真，不控制台架，不替工程师作工程签核，不擅自调用收费或外部模型，不建立生产集成或发布站点。页面中不得把模拟结果、拟实现能力或目标指标写成已验证成果。

## 四 统一演示数据与业务主线

### 4.1 场景与字段

创建项目 P01。协议初版包含发动机最大扭矩 2600 N·m、12 档 AMT、需要取力器、总成重量 ≤300 kg，以及“耐久按双方商定标准执行”的未明确条款。基型 JX-12A 额定输入扭矩为 2600 N·m、无取力器。BG-01 将发动机最大扭矩变更为 2800 N·m。以上均为演示假设。[S2 第 3.4 节]

发动机最大扭矩是整车输入条件，变速器额定输入扭矩是产品要求，必须分别建模。新增一条派生要求“变速器最低额定输入扭矩 ≥ 发动机最大扭矩”，保存派生关系与来源。不能因数值相同把两个参数合为一条。

| 显示编号 | 语义 | 初版与变更 |
| --- | --- | --- |
| REQ-P01-B-003 | 发动机最大扭矩，源参数 | 2600 → 2800 N·m |
| REQ-P01-C-002 | 变速器最低额定输入扭矩，派生要求 | ≥2600 → ≥2800 N·m |
| REQ-P01-C-001 | 档位数 | 12 档 |
| REQ-P01-C-006 | 取力器功能 | 需要 |
| REQ-P01-D-002 | 总成重量上限 | ≤300 kg |
| REQ-P01-F-001 | 耐久要求 | 标准未明确，保留待澄清状态 |

C-002、F-001 及固定分母规则是本次为开发验收增加的设计细化。显示编号可读，内部主键另用稳定唯一 ID。材料中额外出现的速比、接口等要求必须被保留；若未纳入固定验收集合，要显示范围及理由，不能为凑覆盖率静默删除。

### 4.2 主线演示步骤

1. 从空演示数据库导入协议，抽取字段和证据；无法确认的条款形成可见问题。
2. 工程师修订并确认需求，查看候选基型、差异和可复用件。
3. 生成并分别确认设计评审、DFMEA、试验方案与用例。
4. 查看追溯矩阵，耐久要求因缺少判定依据而未覆盖。
5. 导入 BG-01。源参数与派生要求更新版本，受影响设计、FMEA、用例和相关报告进入待复核；无关条目保持有效。
6. 展示旧图纸仍写 2600、试验加载基准仍为旧版等冲突；同时呈现模拟样件孔位不符及供应商响应滞后。
7. 工程师修订、确认并重新试验；新的实测失败仍必须显示，不因完成复核而自动通过。
8. 根据明确的模拟补充协议澄清耐久条款，增加对应有效用例和执行证据。
9. 复检、处理问题，导出草稿或满足门禁的材料包；只有明确人工审批才形成演示评审通过记录。

### 4.3 覆盖度与试验通过口径

固定验收集合为 C-002、C-001、C-006、D-002、F-001 五条需验证要求。发动机源参数不重复计入分母，但其派生要求必须纳入。分母由受控范围清单决定，不由解析器提取多少条决定。

有效覆盖率 = 至少拥有一个已确认、依据当前版本且具备完整工况和判定标准的用例的需求数 ÷ 范围内需验证需求总数。无试验执行结果不影响“计划已覆盖”，但会影响验证完成和评审就绪。未澄清耐久仍在分母中。

预期：初次生成有效计划时为 4/5 = 80%；扭矩变更使相关用例失效后为 3/5 = 60%；修订并确认扭矩用例恢复为 80%；明确耐久并补齐有效用例达到 100%。这些是合成验收场景结果，不是产品准确率或项目效果实测。

TC-007 静扭强度试验须同时记录加载基准 2800 N·m 和示意判定标准“后备系数 ≥2.5”。实测 2.4 应失败；不得将后备系数直接与 2800 比较。旧运行即使在 2600 基准下通过，也不能作为新版通过证据。补充通过样例可用后备系数 2.6，并明确它仅为合成测试数据。

## 五 数据与状态设计

### 5.1 最小领域对象

| 对象 | 必备关系或字段 |
| --- | --- |
| Project | 稳定 ID、显示编号、范围清单、当前阶段 |
| SourceDocument 与 Evidence | 文档版本、内容哈希、原文、可验证位置、输入模式 |
| Requirement 与 RequirementRevision | 稳定身份、类别、值与单位、约束、来源、派生关系、版本 |
| ProductBase 与 VariantPoint | 基型版本、匹配依据、差异、影响零件、需求版本 |
| ReviewItem 与 FmeaItem | 独立 ID/版本、依赖、内容、负责人、审核记录 |
| TestPlan 与 TestCase | 目的、条件、指标、标准版本、需求/FMEA 版本集合 |
| TestRun | 用例版本、工况、实测、单位、结果、执行证据，不可回写历史 |
| SampleDelivery 与 Comparison | 文件、图号、样件记录、规则/模拟/人工模式、问题关联 |
| Communication 与 CoordinationMetric | 议题、参与方、事件时间、统计窗口、计算规则版本 |
| Issue 与 ConsistencyFinding | 稳定问题 ID、对象版本、严重度、证据、处置和复检状态 |
| ReviewDecision 与 AuditEvent | 操作者、角色、对象版本、决定、理由、时间、前后变化 |
| GatePackage | 冻结快照 ID、材料清单、哈希、依赖版本、模式、门禁与人工决定 |

可以按现有架构合并存储表，但不能丢失上述语义。业务对象使用 UUID 或等效稳定主键，显示编号另存；不可用数组位置、当前条数或参数名称充当身份。

### 5.2 状态规则

分开保存四类状态：审核状态 draft/pending_review/confirmed/rejected；版本有效性 current/stale；执行状态 not_run/running/completed；符合性 pass/fail/incomplete/invalid。名称可以映射，但不能用一个 reviewed 布尔值替代。

每个生成产物初始为草稿，明确的人工动作产生确认记录。FMEA、试验方案、样件比对及评审需要各自的确认语义。确认记录附着于具体版本，不得因为上游确认而批量假定下游已经审核。

上游实质变更在同一事务中保存新版本、传播失效、记录审计。反复提交同一命令须幂等或明确拒绝。无变化重新解析不得平白创建新版本；识别有歧义时形成待人工合并的候选，不按名称或行号悄悄覆盖。

历史试验结果与确认记录保留；P0 对新版本采用新用例版本和新执行记录，禁止直接把旧结果改挂新版。同一当前用例的最新执行失败或证据不足必须显示并阻断，不能筛选旧通过结果掩盖；排序与撤销规则须明确并留痕。复用旧实测的正式适用性审批作为 P1 独立设计。删除被引用内容采用软删除或阻止删除，并说明影响。

### 5.3 门禁与材料包

允许任何阶段导出标明缺口的 draft 草稿包。ready_to_submit 为系统根据规则计算的就绪状态：必需需求与产物已确认且 current；有效覆盖达到该受控场景规定门槛；全部必需验证有适用的通过证据；不存在未关闭的阻断冲突或关键缺失。

本固定演示集合要求五条全部覆盖和验证，门禁为 100%；这不改变申报书整体覆盖度目标 ≥90% 的含义。项目风险需已处理或由演示负责人明确接受并留理由，不能自动清零。

human_approved 只由人工对冻结材料包作审批产生。导出成功不等于 ready_to_submit，ready_to_submit 不等于 human_approved。使用模拟视觉或模型结果的包仍须注明模式，不能因此宣称真实工程认证。

## 六 功能与界面实现要求

### 6.1 页面组织

保留总览、需求解析、变型设计、试验验证、一致性检测、协同预警、知识库、项目管理和设置的主导航。增加需求详情/版本记录、问题详情/证据、材料包预览等上下文页面或抽屉，避免无意义增加导航。

总览数字、进度和趋势从真实状态或有标签的样例事件计算。每个关键条目可跳转来源和关联对象。按钮均有可验证行为，具备加载、空态、错误态和成功反馈。中文界面优先适配 1440×900 与 1366×768；宽表可横向滚动，状态不能仅用颜色区分。

### 6.2 输入与生成

文本型 PDF、DOCX、TXT 以及约定 JSON/CSV 通过后端真实解析。默认单文件上限 8 MiB，可配置并在前后端一致校验。DOCX 使用段落或表格定位；没有可靠页码时不得编造。扫描件缺乏 OCR 时清楚提示，允许手工补录，不能虚构识别结果。

规则解析保留同参数重复、矛盾、缺失和非数值条件。模拟输出须绑定已识别场景或结构化输入；未知材料返回未识别/待人工处理，不能对任意上传文件返回同一组预置需求。置信度无法计算时留空并注明来源，不填装饰性百分比。

所有生成结果经过 schema 校验，记录 mode、输入版本、规则/适配器版本与证据。mode 至少区分 rule、mock、manual，未来接入模型后再增加真实模型来源信息。模式在界面和导出中均可识别。

### 6.3 规则与协同指标

数值处理正确区分严格与非严格比较，统一千位分隔符、约定单位和小数精度。空值、非法值、未知单位或工况不足返回明确状态。温度 20 ℃ 落在 -40～50 ℃ 内，只说明单点处于范围，不能证明全范围性能通过。

型谱采用受控字段和可解释评分；硬约束不满足要标记，不能被高总分掩盖。DFMEA 的 RPN 按 S×O×D 计算，S/O/D 使用合成量表并由工程师确认，不按行号生成数值。审核未完成与检测失败可以同时存在。

协同输入至少含议题 ID、发起/响应事件、参与组织、应参与方、截止时间及时间戳。冻结响应配对、未回复、议题重开、缺席和统计窗口的定义。没有足够数据时显示不可计算，不默认零风险。协调成本基于输入工时与费率真实算术计算，单价明确为合成假设。

风险评分先采用下列可验收的演示规则，记为 COORD-DEMO-V1；M0 如需调整必须同步夹具和预期，不得静默更改。它是透明的演示规则，不是经验证的预测模型。任何“预计延期”或预警时间若采用样例输出，均注明模拟，不能据此声称提前两周预测已实现。

协同最小夹具使用同一统计窗口：三组通过 replyToId 明确配对的请求与响应耗时分别为 48、52、56 小时，平均为 52 小时，样本数为 3；四个显式 reopened 事件计为反复 4 次；应参与方为主机厂、法士特、S-02，实际只有后两者发言，缺席率为 1/3。未回复记录单独显示待响应及截至窗口末的等待时长，不以 0 混入已响应平均值。

COORD-DEMO-V1 的三项条件为平均响应 >48 小时、反复 ≥3 次、缺席率 ≥1/3；命中 0 项为低、1 项为中、至少 2 项为高。缺必要数据则显示数据不足，不能降为低。上述夹具命中 3 项，显示高风险及三条原因。若需要分数，可用命中项数÷3×100 并注明规则指数及舍入方式。人工输入协调工时 6 小时、演示费率 200 元/小时，示例估算成本为 1200 元；不从消息条数推算工时。

### 6.4 材料导出

P0 导出 ZIP，至少包含 manifest.json、可阅读的中文 HTML 总报告、需求与设计/DFMEA/试验 CSV、追溯矩阵、冲突与协同记录、审核日志及必要证据索引。报告无需依赖外网脚本或字体，便于本地打开和打印。原件是否纳入材料包使用明确选项，不自动塞入无关或未授权文件。

导出采用一致性快照，记录项目、对象版本、时间、模式和文件哈希。导出后的包不随项目继续编辑而变化。测试必须打开 ZIP、解析 manifest 和关键文件、核对 ID/版本/中文内容；只验证按钮或 HTTP 200 不算完成。更丰富的 DOCX/PDF 材料格式列 P1。

## 七 技术架构与工程约定

### 7.1 推荐技术方案

若没有已存在的正式仓库，建议采用以下组合；如果已有可运行仓库，优先保持其技术栈并记录差异。初始化时验证版本兼容性、记录运行环境并提交锁文件，不直接依赖未锁定的 latest。

| 层次 | 推荐方案 | 职责 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 中文工作台、表单、状态与追溯展示 |
| 后端 | FastAPI 与类型化输入输出 | 应用服务、规则、生成适配、导出和业务校验 |
| 数据 | SQLite 与显式迁移 | 版本、关系、审核、试验执行与项目持久化 |
| 后端测试 | pytest | 领域不变量、规则、真实临时数据库与 API 集成 |
| 前端测试 | Vitest、Testing Library | 交互行为、错误反馈及状态呈现 |
| 端到端 | Playwright | 连真实本地前后端跑主线，验证下载和重启 |

Vite 官方提供 react-ts 模板；FastAPI 官方数据库教程包含 SQLite；测试工具官方文档提供各自的测试与本地服务能力。上述采用是本项目的工程判断。[T1–T7]

### 7.2 模块与接口原则

界面、应用服务、领域规则、数据存储和外部适配分层。后端是业务数据及判定的权威来源。前端 localStorage 只保存界面偏好，不将整库状态反复覆盖后端，也不实现另一套不一致的通过判定。

建议目录为 frontend/、backend/、tests/e2e/、fixtures/、scripts/、docs/、reference/。原始材料存 reference/；开发规范 AGENTS.md 放仓库根目录。fixtures 同时包含协议初版、变更单、候选基型、历史项目、样例图纸/样件、沟通记录和明确预期。

API 按项目、文档、需求版本、确认动作、生成任务、用例与执行、问题、指标、材料包划分。变更请求携带 expected_revision，冲突明确返回；领域操作不以全量 /api/state 覆盖替代。具体路由与错误格式在 M0 固定并写 OpenAPI/接口说明。

生成服务、视觉服务和风险预测通过可替换 Provider 接口实现。默认适配器不访问公网；真实模型调用仅在有明确授权、实际配置和独立测试时启用。浏览器端不保存模型密钥。Provider 合同应包含输入 schema、结果 schema、模式、来源、超时与失败语义。

### 7.3 运行与数据保护

默认仅监听 127.0.0.1；无真实认证的演示实例不直接暴露公网。上传文件只作为数据处理，不执行其中代码或指令。限制路径、类型、大小及归档内容，防止覆盖任意文件；备份恢复先验证结构、引用和版本，并在替换现有数据前取得界面确认。

服务启动不重置数据库。种子数据用显式命令导入，重复执行可预测。所有测试使用独立数据库与临时文件。日志保留审计必要字段，不记录密钥或不必要的完整企业原文。安装说明给出实际验证的环境与命令，并记录操作系统限制。

## 九 TDD 与质量门槛

### 9.1 开发循环

新增业务行为和缺陷修复必须遵循 RED → GREEN → REFACTOR。先写最小验收测试，运行并确认因为预期业务能力缺失而失败；再写最小实现；最后在测试保护下重构。依赖未安装、路径错或语法错不算有效业务 RED。禁止先完成实现再补测并声称采用 TDD。

遗留问题先建立回归测试。不能删除断言、随意 skip 或放宽规则换取绿色。纯文案和排版使用相应检查，不写没有业务价值的测试。环境不能运行时记录未执行或阻塞，绝不伪造通过。

### 9.2 分层测试

| 层次 | 必测范围 |
| --- | --- |
| 领域单元 | ID、revision、派生关系、失效传播、数值与工况、覆盖、门禁、评分 |
| API 与存储集成 | 临时 SQLite、迁移、事务回滚、版本冲突、导入、快照、重启 |
| 前端组件 | 编辑确认、双重状态、来源跳转、失败反馈、禁用与可操作条件 |
| E2E | 协议到材料包完整流程、变更后复核、异常输入、下载内容与持久化 |
| Provider 合同 | 合成替身的输入输出 schema、来源、超时、未知场景与错误处理 |

默认验收门槛为核心领域分支覆盖 ≥90%；有效业务代码语句覆盖 ≥80%。在适用的 Python 与 TypeScript 代码分别计算；无某类代码则标不适用并解释。排除生成代码、第三方和纯样式时列出路径与理由，不用另一端高覆盖掩盖风险。

默认测试禁止公网模型和收费请求。至少一条完整 E2E 连接真实本地 API 与 SQLite，不将全部 API mock 后宣称联调完成。AI/外部服务可以替换，版本流转、数据库和材料导出不能在最终闭环验收中整体替换成假结果。

### 9.3 证据与开发记录

每个核心任务记录验收编号、变更范围、RED 命令与失败断言、GREEN 结果、重构回归及证据路径。保存原始输出和运行环境信息；在 docs/DEVELOPMENT_LOG.md 追加日志，在 docs/DECISIONS.md 记录方案与范围变化。真实运行前不预填测试时间、通过数、覆盖率或截图。

开发 AI 的最终报告必须说明实际完成范围、已执行命令及结果、未执行项、已知限制、安装启动方法和演示步骤。代码、日志、测试报告和交付状态应能相互核对。

| AC-14 | O12 上传与记录可用；人工/模拟视觉清楚标识；问题关闭后需复检或有明确处置依据 |
