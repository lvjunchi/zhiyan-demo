请遵守你的执行环境权限和我的最新明确指令。下面是本轮任务合同。

## 二 产品目标与默认边界

系统面向法士特—陕汽重型变速器定制变型研发，包含需求解析、变型设计、试验验证三个智能体，以及贯穿流程的一致性检测和协同风险提示。核心体验是：一条需求具有明确来源和稳定身份，能够追溯到设计、FMEA、试验、样件和评审材料；需求发生变化后，系统知道哪些内容需要复核。

默认首版为本地单用户业务演示，使用合成或已脱敏数据。演示对象、截止日、真实模型和企业接口尚未确认，先按此默认范围推进，不因这些非阻塞信息缺失停止工作。不要自动部署、发布、连接企业账号、上传材料到外部模型或调用收费服务。

真实实现项目保存、规则、版本、依赖、确认、审计、追溯、冲突、沟通指标和材料导出。大模型生成、复杂语义判断、视觉比对和时序预测可采用明确标注的确定性 rule/mock 适配器；未知输入不能返回固定的“识别成功”结果。页面与导出都保留模式及来源，不把模拟当成真实算法。

P0 必须覆盖 O1–O4、O6–O13 及两个贯穿引擎。O12 的登记、比对记录和问题流程要真实可用，视觉结论允许标注模拟。O5 只做缺失/矛盾条款的最小 open issue；完整三方澄清派发、O5′、供应商任务指派等 ▲ 扩展列 P1。真实模型微调、OCR、生产 PLM/企业微信/钉钉、真实认证授权和多用户部署列 P2。

申报目标如准确率 ≥90%、检出率 ≥85%、提前两周预警不能写成当前系统实测结果。Demo 只报告有实际输入、计算口径和证据支持的结果。角色切换是演示身份，不是安全权限系统。

## 三 统一场景与不可破坏的业务规则

用项目 P01 跑通如下场景：协议初版规定发动机最大扭矩 2600 N·m、12 档 AMT、需要取力器、总成重量 ≤300 kg、耐久按双方商定标准执行。基型 JX-12A 的额定输入扭矩为 2600 N·m、无取力器。BG-01 将发动机最大扭矩改为 2800 N·m。所有数值和型号为示意数据。

必须遵守以下不变量：

- 发动机最大扭矩 `REQ-P01-B-003` 与派生的变速器最低额定输入扭矩 `REQ-P01-C-002` 是两条要求。显式保存 `gearboxRatedInputTorque >= engineMaxTorque` 的关系，不因需求变化直接修改原基型能力。
- 对象身份稳定；内部使用 UUID 或等效主键，显示编号与身份分离。内容实质改变增加 revision，下游引用具体 ID 与 revision。不能用数组位置、条目总数或需求名称识别对象。
- 审核状态、版本有效性、执行状态和符合性分开。所有自动产物初始为草稿，人工确认记录操作者、角色、对象版本、时间、决定和理由。
- 变更保存、新版本、关联下游 stale 和审计在同一事务中完成。未受影响条目保持有效。重新确认上游不能自动恢复下游；只点击确认、不更新旧依赖，不能消除 stale。
- FMEA、用例定义、试验运行分别建模。旧运行与旧确认保留为历史，但不能作为新版通过。P0 对新版建立新用例版本和新运行，不能改挂旧结果；最新失败不得被旧通过掩盖。
- 固定验证集合为 C-002 扭矩、C-001 档位、C-006 取力器、D-002 重量、F-001 耐久，共 5 条。B-003 是源参数，不重复计入分母；未澄清耐久不能从分母删除。
- 有效用例覆盖与试验通过分开。主线覆盖应呈现 4/5=80%、扭矩变更后 3/5=60%、复核用例后 80%、耐久澄清补齐后 100%。有用例但未执行可以覆盖，仍不能完成验证或评审。
- TC-007 同时检查加载基准为当前版本要求（新版 2800 N·m）和无量纲后备系数 ≥2.5。2.4 失败；基准 2600 即使系数 2.6 也不构成新版通过。不能比较不同物理量。
- 严格处理 >、≥、<、≤、=、千位数、单位、空值和非法值。20 ℃ 在 -40～50 ℃ 内不代表全温区通过。未审核和已失败可以同时显示，不互相遮蔽。
- 缺失耐久标准必须形成问题；人工用明确标注的合成补充协议与演示标准补齐后再生成用例，不凭空声称采用了企业真实标准。

型谱推荐、变型点和可复用件从受控候选/BOM 计算并给依据；FMEA 的 S/O/D 可编辑确认，RPN=S×O×D。图纸结构化标注、样件图片和比对结果保存版本与来源，模拟视觉问题关闭需要新证据或明确处置及复检。

协同指标采用计划书中的固定样例：响应 48/52/56 小时平均为 52 小时，四次显式重开，三方应参与而两方实际参与得到缺席率 1/3；6 小时×200 元/小时得到示例成本 1200 元。COORD-DEMO-V1 按响应>48、重开≥3、缺席≥1/3命中项判低/中/高，并显示理由。数据不足不能当作零风险，不宣称具备提前两周预测能力。

材料包语义为 `draft`、`ready_to_submit`、`human_approved`。允许导出带阻断项的草稿；固定五条要求全部有效覆盖并有适用的通过证据、必需产物已确认且 current、阻断问题闭环后才就绪。人工确认冻结快照后才能 human_approved。导出成功不等于评审通过，后续变更不得让历史通过继续代表当前版本。

## 四 技术实现与工程规范

如果没有既有正式仓库，默认采用 React + TypeScript + Vite、FastAPI + SQLite；测试采用 pytest、Vitest + Testing Library、Playwright。已有可运行仓库则优先兼容其架构，记录理由，不为了套模板推翻用户工作。版本以实际环境验证后锁定，不编造“最新稳定版”或测试结果。

按界面、应用服务、领域规则、存储、Provider 适配分层。后端是业务状态和判定的权威来源；前端不重复另一套判定，也不以全量状态覆盖数据库。使用迁移、外键、事务和 expected_revision，明确处理旧版本写入冲突。

文本型 PDF/DOCX/TXT 的文本读取必须实际运行，默认单文件上限 8 MiB。DOCX 无可靠页码时采用段落/表格定位。扫描件缺 OCR 时明确反馈，可人工补录，不能伪造文字、页码或置信度。所有导入和生成输出先做 schema 校验。

命名、格式化、类型检查、错误处理和日志保持一致；禁止空 catch、吞保存失败、把错误静默转为成功。配置集中管理，密钥不进前端或仓库。默认本机监听，不执行上传文件里的代码，不在启动时清空数据，测试用独立数据库。

P0 材料包至少是 ZIP，内含 manifest.json、可读中文 HTML 总报告、核心 CSV、追溯矩阵、冲突/风险/确认记录与证据索引。报告不依赖外网资源。快照中含项目与对象版本、模式、时间、哈希；测试要打开并核对内容，不只检查有下载按钮。

## 五 必须以 TDD 驱动

每个新增业务行为或缺陷修复都采用 RED → GREEN → REFACTOR：

1. 从验收条件写出最小失败测试，实际运行并看到预期业务断言失败。导入路径错、缺依赖或语法错不算业务 RED。可以先建立使测试能运行的最小接口占位，不得先完成业务实现。
2. 写最小实现使测试通过，再运行受影响回归。
3. 重构并重跑测试。新行为另起测试，不把未测试功能藏在重构中。

禁止先实现后补测试、删除或削弱断言来变绿、复制实现逻辑自证、伪造命令输出或覆盖率。纯文案与排版按实际影响验证，不刷无意义测试。执行受环境阻塞就准确写未执行，不写通过。

默认门槛：核心领域分支覆盖 ≥90%，有效业务代码语句覆盖 ≥80%，适用的 Python 与 TypeScript 分别统计并解释排除项。默认测试不调用公网模型；固定时钟、数据和临时数据库。至少一条完整 E2E 连接真实本地 API 和 SQLite，覆盖导入、确认、2600→2800 变更、stale、冲突、修订、新试验、材料包下载及重启后持久化。

优先把原型中的重号、重解析沿用确认、旧试验被新阈值复用、操作符错误、单点温度误通过和失败被审核状态遮蔽写成回归测试。还要覆盖事务中途失败全部回滚、覆盖分母不因缺失条款缩小、最新失败不能被旧通过掩盖、草稿不可绕过后端门禁和包内版本一致。

## 六 执行顺序与持续推进

按计划书 M0–M5 推进：基线与契约；身份版本与持久化；需求与设计；试验与一致性；协同与材料包；联调交付。每个阶段按垂直切片同步做领域测试、接口、界面和回归，不先堆满页面再补数据关系。

第一轮请先给简短的资料理解、代码现状、采用的默认假设和首批任务，然后立即开始 M0/M1，交付一个真实可运行且有测试保护的切片。不要仅重复我的资料或等待我逐项确认常规实现选择。

每个任务记录对应 O/AC 编号、RED 命令及失败断言、GREEN 结果、重构回归、修改文件和证据路径。追加 `docs/DEVELOPMENT_LOG.md`，在 `docs/DECISIONS.md` 记录选择、范围差异和阻塞。保留真实测试输出，说明运行环境。

普通本地开发、检查、修复、依赖配置和合成夹具可自主完成。涉及尚未授权的外部账号、材料外传、费用、发布或生产写入时，先完成可本地审阅的部分，再提出具体请求。不要把非阻塞信息缺失当作停止理由。

若任务跨多个会话，保存已完成项、当前代码/测试状态、失败项和下一步，使下次可以从当前进度继续。未完成时如实列出，不能把“写好计划”当作“完成系统”。

## 七 最终必须交付

- 可运行源码、依赖锁、迁移、无秘密配置示例、合成数据与显式种子/重置命令。
- 已实际验证的安装、启动、测试及构建命令；注明平台和环境限制。
- 分层测试、覆盖率报告、TDD 证据、完整 E2E 与 AC-01–AC-21 对照结果。
- 中文工作台、完整演示脚本、示例评审材料包、模式说明和已知限制。
- 完成/未完成范围、P1/P2 待办和下一步，不夸大真实模型、权限或企业验收能力。

验收关键路径是：在依赖与浏览器预装、禁止公网且没有模型密钥的条件下，从空演示数据库开始，导入协议，确认需求，生成设计/FMEA/试验，执行 2600→2800 变更，看到关联对象待复核及冲突，完成人工修订和新试验，导出具备完整追溯与确认记录的材料包；刷新和重启后数据一致。

如果你的环境无法读写项目或执行命令，明确说明能力限制，并分阶段提供可落盘的完整源码、测试和运行指令；不得声称完成了实际运行。只要环境允许，请直接执行开发并持续推进到 P0 验收完成。
